# PulseTwin narrated demo script

Synthesized narration over actual application captures and technical slides. Not a live clinical demonstration.

## 01. Personal health, simulated.

Welcome to PulseTwin, a personal blood pressure digital twin prepared for Team Gimites. The team leader is Yashwanth M, joined by Kalashikam Vijay Krishna, Subiksha K, and Shakthi K. This version adds ten research features to a working, interpretable prototype. We will explore scenario comparisons, saved settings, daily observations, data quality, trends, sensitivity, errors, uncertainty, shareable hypotheses, and printable evidence. The central idea remains simple: daily observations should help us ask better questions about possible futures. Every example uses synthetic data, and no clinical accuracy or treatment benefit is claimed. This voiceover is synthesized, with captures from the running application. The code, architecture, model card, tests, and presentation are included so reviewers can reproduce the walkthrough and inspect its assumptions.

## 02. A chart tells only half the story.

Imagine a person with three months of blood pressure readings, step counts, sleep notes, dietary estimates, and self-reported stress. A conventional chart can show a trend, but it cannot explain how these measurements fit together for that individual. A generic wellness score often hides the relationship behind a single number. PulseTwin explores a different interaction: make the personal model visible, let the user specify a hypothetical scenario, and show the uncertainty next to the result. This is a research problem rather than a promise to lower blood pressure. Many important drivers are unmeasured, and lifestyle variables can be correlated with each other. Our design treats those limitations as part of the product. The goal is to support informed questions, not to turn observational patterns into prescriptions.

## 03. One focused healthcare use case.

The selected use case is longitudinal cardiometabolic research and education, with systolic blood pressure as the single modeled outcome. A researcher or an authorized user can inspect how a person's observations relate to daily habits and explore a conditional future. We deliberately avoid a broad health score, disease diagnosis, medication recommendations, and automated clinical decisions. A narrow outcome makes the model easier to inspect and the prototype easier to validate. The application does not contain a physician workflow, electronic health record integration, or a live wearable connection. Those are possible future integrations, not features we claim today. The complete implemented loop is observation ingestion, validation, personal fitting, residual state updating, scenario simulation, and review. Keeping this scope explicit is essential to evaluating the submission fairly.

## 04. A working research workspace.

Here is the running dashboard. The active profile is Asha, a fictional label attached to a deterministic synthetic dataset. The profile bar states the observation count and date range. Across the top, three cards separate current modeled systolic pressure, the chosen scenario at the selected horizon, and held-out prediction error. The current number is a model estimate at the most recent seven-day average habits; it is not simply the last cuff reading. The scenario number depends on the controls at the right. Prediction error comes from a separate chronological evaluation. Keeping these three concepts distinct prevents a future scenario from being mistaken for a measured reading or an accuracy guarantee. Notice also the persistent research notice and the synthetic data badge. These disclosures remain part of the normal workflow.

## 05. A new day. A reviewed update.

The first two new tools strengthen the observation loop. The daily update form selects the next consecutive date automatically. Enter a systolic reading and daily habits, then add the observation. The server validates the complete sequence before the new history replaces the active session. The model is refitted, and the interface shows the modeled current pressure before and after the update. Updated observations remain selectable during the session and can be exported as CSV. Alongside this, data-quality review identifies unusual readings, large daily changes, constant predictors, and highly correlated inputs. These are transparent engineering heuristics rather than clinical thresholds. They never silently remove or repair a row. A clean review is not a medical certification. The purpose is to expose measurement context and weakly identified associations before interpreting a scenario.

## 06. A model you can inspect.

The first modeling layer is Bayesian linear regression. Four standardized habit features and an intercept describe systolic pressure. Each person gets a separate fit. There is no pretrained neural network, external language model, or hidden population dataset. Gaussian priors regularize the coefficients so a small or correlated history does not lead to an unconstrained fit. The posterior mean and covariance are calculated directly using NumPy matrix operations. The prior values are illustrative engineering choices, not clinical effect sizes copied from a trial. In particular, the model does not prove that increasing one habit will cause a particular change in pressure. It estimates an association conditional on the recorded inputs. The repository contains the exact feature scales, prior values, equations, noise assumptions, and limitations in the model card.

## 07. Updating the twin over time.

A static regression alone would not capture the concept of an updating twin. PulseTwin adds a scalar Kalman filter over the residual pressure after the regression prediction. This state represents slow unobserved drift without naming it as a specific disease mechanism. Each daily residual adjusts the current state using a Kalman gain, while process variance expresses additional uncertainty over time. When a new history is imported, the personal coefficients are refitted and the residual sequence is filtered again. This is a two-stage approximation, not a joint physiological state-space inference system. The covariance does not capture every dependency between coefficients and state. The implementation is a human-in-the-loop, data-driven twin prototype. It provides a repeatable observation and simulation loop, while continuous sensor synchronization and clinical feedback are explicitly future work.

## 08. Compare and keep useful hypotheses.

The scenario comparison tool lets a reviewer pin the current settings as a reference, change the controls, and simulate a second possibility. Both curves are recomputed against the same active observations, horizon, and interval level. Switching profiles recalculates the reference rather than carrying an old person's prediction into the comparison. The displayed endpoint difference is a difference of conditional means, not an estimated treatment effect. The adjacent library saves up to eight named settings in the current browser. An entry contains a generic label, four hypothetical inputs, horizon, and interval level. It does not contain observation records, profile identity, or fitted results. Load an entry to apply it to the current history, or delete it from the library. This makes repeated experimentation convenient while keeping the data boundary clear.

## 09. Choose the lens. Keep the uncertainty.

The uncertainty lens now supports eighty, ninety, ninety-five, and ninety-nine percent predictive intervals. Select a level in the scenario studio. The forecast band, legend, exported report, and held-out coverage all update consistently. The model's predicted mean does not change. A wider band is not evidence that the model became more accurate; it expresses a different coverage statement under the same assumptions. The band combines coefficient uncertainty, residual-state uncertainty, fixed observation noise, and process variance over the horizon. It still does not capture every source of confounding, measurement bias, changing medication, or model misspecification. The uncertainty panel states the endpoint interval and its width explicitly. Tests verify that interval widths expand with confidence while the mean stays fixed. This makes the uncertainty control meaningful rather than a cosmetic chart setting.

## 10. Change one input. Inspect the response.

The sensitivity explorer asks a narrower question than changing four controls together. Choose movement, sleep, sodium, or stress. The model evaluates seven target values for that one input while holding the other scenario settings fixed. The curve shows the projected systolic pressure at the current horizon. The sweep stays within the intersection of observed values and permitted scenario bounds. If that intersection is empty, the application reports that no valid sweep is available. The personal coefficient and its ninety-five percent interval are also shown. This coefficient interval is labeled separately from the selectable predictive interval, because they describe different quantities. Correlated or constant inputs can make coefficients poorly identified. The sensitivity curve is therefore an inspectable association, not a recommended intervention. Automated checks compare sweep outputs against direct scenario simulations.

## 11. See the trend. Inspect the misses.

Two additional panels show information that a single accuracy number hides. Longitudinal trends plot the seven-day rolling mean and summarize the latest week's pressure, its change from the previous week, and recent variability. A recent linear slope is descriptive history, not an attributed cause or a forecast. Error diagnostics show each held-out observation beside its prediction and signed residual. Positive bias means the model tends to underpredict. Root mean squared error highlights larger misses, while maximum absolute error exposes the worst miss in the small holdout. The evaluation still fits only on the chronological training prefix. Held-out pressure labels do not enter the fit or state update. Held-out daily habits are known inputs, so this remains conditional prediction. These panels make both the history and model failures easier to question.

## 12. Measured prototype outcomes.

On the included synthetic fixtures, Asha has a twin mean absolute error of three point zero one millimeters of mercury, Dev has three point one nine, and Mira has two point eight one. The training-mean baselines have errors of three point six zero, three point eight five, and four point four seven respectively. The last-reading baselines are weaker on these fixtures. All fourteen held-out readings fall within the predictive interval for each profile. That does not establish reliable calibration, because fourteen examples are a tiny sample and the bands may be conservative. More importantly, the synthetic generator uses approximately linear relationships similar to the fitted model. These results demonstrate that the implementation behaves sensibly on its fixtures. They are not evidence of clinical accuracy, causal benefit, or generalization to real patients.

## 13. Share the question. Export the evidence.

The shareable-settings action creates a URL containing only the hypothetical inputs, horizon, interval level, and a schema version. It excludes observation history, profile identity, and predictions. A recipient applies those settings to their own active data. The application validates the values and rejects malformed links, including when a link is opened in the same tab. A local address still requires an accessible application instance; this is not a claim of a publicly hosted demo. The printable report provides a second handoff path. It collects the current model version, data provenance, observation period, scenario assumptions, predicted endpoint, interval, holdout metrics, review flags, and limitations in a clean PDF-ready layout. Unlike the settings link, a report may identify its active profile. The user should share it only with authorization.

## 14. Simple architecture. Real endpoints.

The implementation has a deliberately small architecture. A static browser application handles interaction and visualization. FastAPI serves the interface and exposes health, synthetic profile, CSV import, and analysis endpoints. Pydantic validates JSON and parsed CSV observations. NumPy computes the Bayesian fit, filtered state, scenario, and chronological evaluation. The server returns a structured report, which the browser renders and can download. There is no database, analytics service, external model provider, or paid API dependency. After package installation, the application works without external network calls. The architecture document shows both the request flow and the trust boundary. This simplicity makes the prototype easy to inspect and run, but it is not production security. Authentication, secure deployment, retention controls, and clinical governance would be required before handling real patient workflows.

## 15. Validation beyond a screenshot.

The repository now includes twenty-four automated model and API tests. New checks verify that confidence levels change widths without changing means, known linear histories produce the expected trends, and quality flags do not remove observations. Constant and correlated predictors, empty sensitivity ranges, exact residual metrics, and parity between sensitivity curves and direct simulations are also covered. The daily update test confirms that an additional observation changes the personal model. Browser acceptance uses real Chromium to exercise all ten new workflows and the original dashboard. It verifies saved settings survive reload, deletion works, shared links omit observations, invalid links are rejected, session updates retain provenance, and a printable PDF is produced. Mobile overflow and JavaScript errors are checked as well. These are engineering tests, not clinical validation.

## 16. Boundaries are part of the product.

PulseTwin includes three deterministic synthetic profiles and no patient records. The application has no server-side persistence and makes no external AI calls. Uploaded observations travel to the local API and remain in request memory and the active browser session. A downloaded report contains its underlying observations, so exporting is a deliberate data-handling action. The prototype does not have user authentication, clinical access controls, or production hardening, and it should remain local during evaluation. Model warnings explain observational uncertainty and identify scenarios beyond the observed input range. Important variables such as medications, comorbidities, measurement timing, and kidney function are absent. Those gaps are substantive limitations, not minor disclaimers. The prototype helps inspect a hypothesis; it does not diagnose, prescribe, triage symptoms, or claim regulatory approval.

## 17. A credible path beyond the prototype.

The next step is not simply adding more visual features. A credible development path starts with consented, well-characterized longitudinal data and a preregistered evaluation plan. We would examine measurement quality, missingness, calibration, and performance across relevant subgroups. We would compare against stronger temporal baselines and test whether the residual state adds value. Clinician review would help define appropriate uses and identify failure cases. Any investigation of intervention effects would need a causal design rather than assuming regression coefficients are causal. Secure ingestion, authentication, data governance, and deletion controls must precede real patient deployment. Live device synchronization could then make the update loop more automatic. Each of these is future work. The present submission delivers a transparent, reproducible starting point whose assumptions and limits can be challenged directly.
